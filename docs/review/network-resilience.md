# Network Resilience Review

**Scope:** sec-tracker — Axum REST backend (PostgreSQL) + React/Ant Design frontend (Vite + Axios + React Query).
**Network surface:** One HTTP server on `0.0.0.0:3000` (backend) consumed by one axios instance on `/api` (frontend, proxied through Vite in dev). No WebSockets, no SSE, no EventSource, no external HTTP client (no `reqwest`, no `hyper::Client`) — the backend never initiates outbound network calls.

| Criterion | Score | Evidence | Recommendation |
|---|---|---|---|
| 1. Reconnection mechanism (auto-reconnect + exponential backoff) | **C** | Frontend: `frontend/src/main.tsx:13` sets `retry: 1` on the global React Query `QueryClient`, which retries failed `useQuery` once (default exponential backoff: ~1s, capped at 30s). Mutations (`useMutation` in `pages/ProjectBoard.tsx`, `pages/ProjectDetail.tsx`, `pages/CommunicationDetail.tsx`, `components/MembersTab.tsx`, `components/PhasesTab.tsx`, `pages/FileLibrary.tsx`) have **no** retry config and no manual retry logic. Backend has no client-side reconnection because it does not initiate outbound HTTP. Vite dev proxy is hardcoded to `http://localhost:3000` (`frontend/vite.config.ts:10-13`) with no fallback target. | Add `retry: (failureCount, error) => …` per query to skip retry on 4xx and back off exponentially on 5xx / network errors. Configure `retryDelay` explicitly. For mutations, wrap user-facing actions in a manual retry helper for transient 5xx/network failures, and disable retry for non-idempotent POSTs that lack server-side idempotency keys. |
| 2. Timeout handling (connect/read/write on every network call) | **D** | DB side: `backend/src/db/pool.rs:23-27` sets `acquire_timeout: 5s`, `idle_timeout: 600s`, `max_lifetime: 1800s` — well-tuned. HTTP side: **no** `tower_http::timeout::TimeoutLayer` or `RequestBodyTimeoutLayer` is applied in `backend/src/main.rs:94-117` — Axum/hyper defaults apply (effectively unbounded on keep-alive). File upload (`backend/src/handlers/files.rs:74-126`) reads the entire multipart body into memory with no per-stream timeout; the only ceiling is `DefaultBodyLimit::max(100 * 1024 * 1024)` (`backend/src/main.rs:116`). Axios client in `frontend/src/api/index.ts:33-35` has **no** `timeout` option, so it defaults to `0` (no timeout) in the browser. `frontend/src/components/FilePreview.tsx:76` uses raw `fetch()` with no `AbortController`/timeout. | Backend: add `tower_http::timeout::TimeoutLayer` (e.g. 30s for headers/body) and `RequestBodyTimeoutLayer` so a stalled client cannot tie up a worker. Frontend: set `timeout: 15000` on the shared axios instance, and pass `{ timeout }` to `filesApi.upload` / `download` with a longer cap (e.g. 60s). Wrap `FilePreview.tsx:76` fetch in an `AbortController` keyed to `open` so unmount cancels the request. |
| 3. Proxy resilience (handle proxy switches / upstream changes gracefully) | **F** | `frontend/vite.config.ts:9-14` hardcodes `target: 'http://localhost:3000'` with `changeOrigin: true`. No environment-based target switching, no fallback target list, no `/api/health` probing. There is no equivalent runtime config in `frontend/src` (no `import.meta.env.VITE_API_URL` use anywhere). Backend has no upstream proxy; it binds directly via `tokio::net::TcpListener::bind("0.0.0.0:3000")` (`backend/src/main.rs:119`) and serves straight through `axum::serve` (`backend/src/main.rs:123`). | Frontend: read the API base URL from `import.meta.env.VITE_API_BASE_URL` (falling back to `/api`), and document it in `frontend/.env.example`. Optionally add a tiny startup probe (`GET /api/health`) with a single retry before rendering the app so the user sees a clear "backend unreachable" state instead of a silent fail. Backend: consider a startup self-check that distinguishes "DB unreachable" from "port already in use" with actionable error messages. |
| 4. Persistent connection health (heartbeat / stale detection) | **C** | No long-lived connections exist (no WS/SSE/polling), so there is no heartbeat to implement. React Query sets `refetchOnWindowFocus: false` and `staleTime: 30_000` (`frontend/src/main.tsx:13-15`) — this means data is treated as fresh for 30s after fetch and is never auto-refetched. The backend `GET /api/health` handler (`backend/src/main.rs:36-41`) is registered at `/api/health`, exposed by `healthApi.check` in `frontend/src/api/index.ts:194-199`, but **never called from any component**. DB pool recycles connections every 30 min (`max_lifetime`, `pool.rs:27`), which is the right defense against stale TCP behind firewalls. | Wire `healthApi.check` into a periodic background poll (e.g. `setInterval` every 30–60s into a `useQuery`) so the UI can show a stale/disconnected banner when the backend stops responding. Consider lowering `refetchOnWindowFocus` to `true` for data that's likely to have changed server-side, or add manual refresh on tab visibility. |
| 5. Network error classification (transient vs permanent) | **D** | Backend (`backend/src/error.rs:36-79`) maps only three sqlx sub-cases: `RowNotFound` → 404, unique/FK/check violations → 400, everything else → 500. No retry-after, no "service unavailable" path. Frontend never inspects the error: every `onError` is `() => message.error('…失败，请重试')` (`ProjectBoard.tsx:79/94/103`, `ProjectDetail.tsx:271`, `CommunicationDetail.tsx:88/97`), and download wrappers do `try { … } catch { message.error('下载失败') }` (`ProjectDetail.tsx:282-294`, `CommunicationDetail.tsx:107-110`). No use of `axios.isAxiosError`, no status-code branching, no distinction between offline / 5xx / validation. | Frontend: write a small `classifyApiError(err)` helper that returns `{ kind: 'offline' \| 'server' \| 'validation' \| 'conflict', message, status }`, then surface different toasts/banners and gate React Query `retry` on `kind !== 'validation' && kind !== 'conflict'`. Backend: add explicit mappings for `sqlx::Error::PoolTimedOut`, `Io`, and connection-level errors to 503 with `Retry-After`. |
| 6. Graceful degradation (when network is unavailable) | **D** | Backend startup is all-or-nothing: `db::build_pool().await.expect("failed to build PostgreSQL pool")` (`main.rs:64-66`) and `migrate::Migrator::new(...).run(&pool).await.expect("failed to run migrations")` (`main.rs:68-73`) panic the process on first failure — no retry, no backoff, no "start in degraded mode". Frontend has no `ErrorBoundary` (grep finds zero matches across `frontend/src`), no service worker, no offline cache. On a network error, React Query just leaves queries in their last state with `error` set; pages render empty data and a single toast. No "you are offline" indicator, no retry button. | Frontend: wrap `<Routes>` in an `ErrorBoundary` (React error boundary or `react-error-boundary`) that renders a "服务暂时不可用" panel with a manual retry. Add `window.addEventListener('online'/'offline', …)` to drive a connection-status chip. Backend: replace the two `.expect()`s with a retry loop (e.g. 5 attempts, exponential backoff up to 30s) so a transient DB outage at boot doesn't crash the container. |
| 7. Connection pool management (HTTP clients / DB connections pooled + reused) | **B** | DB: `backend/src/db/pool.rs:23-28` configures `max_connections: 10`, `acquire_timeout: 5s`, `idle_timeout: 10min`, `max_lifetime: 30min`, with `connect()` (lazy, not `connect_lazy`) — conservative defaults, well commented (`pool.rs:12-17`). HTTP server: `axum::serve` on a single `TcpListener` (`main.rs:119-123`) — hyper manages the HTTP keep-alive pool automatically. Frontend: a single `axios.create({ baseURL: '/api' })` instance (`frontend/src/api/index.ts:33-35`) is reused by every API module, so the browser pools TCP connections to the same origin. No duplicated clients. | Backend: bump `max_connections` once you move past single-user MVP (the comment at `pool.rs:5` acknowledges this). Consider enabling `test_before_acquire: true` so dead connections behind a load balancer are evicted quickly. Frontend: nothing to change — the single-instance pattern is correct. |

## Summary

| # | Criterion | Score |
|---|---|---|
| 1 | Reconnection / backoff | C |
| 2 | Timeout handling | D |
| 3 | Proxy resilience | F |
| 4 | Persistent connection health | C |
| 5 | Network error classification | D |
| 6 | Graceful degradation | D |
| 7 | Connection pool management | B |

**Top three fixes (highest leverage):**

1. Add HTTP timeouts on the Axum server (`tower-http` `TimeoutLayer` + `RequestBodyTimeoutLayer`) and an axios `timeout` in `frontend/src/api/index.ts:33-35`. Without these, a stalled client or a stalled upload can hang a request forever.
2. Replace the two `.expect()`s in `backend/src/main.rs:64-73` with a bounded retry loop so a transient DB outage at startup doesn't kill the process.
3. Wire `healthApi.check` (`frontend/src/api/index.ts:194-199`) into a periodic background poll and an `online`/`offline` listener so the UI can show a real connection-status indicator, and add an `ErrorBoundary` around `<Routes>` (`frontend/src/App.tsx:134-142`) so a thrown query error renders a recoverable fallback instead of a blank page.
